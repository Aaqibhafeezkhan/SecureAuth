# SecureAuth Threat Model

## 1. Security scope

SecureAuth is a local Android TOTP authenticator. It does not implement a backend identity provider, remote account database, password authentication service, HTTP API, or server-side session/token system.

The primary security asset is the user's TOTP secret. The application uses Android Keystore to protect a 256-bit AES key used to encrypt that secret before it is stored in app-private SharedPreferences.

## 2. Security boundaries

### User boundary

The user is trusted to enter a legitimate TOTP secret and to operate the application on a device they control. The application must not expose the stored secret through normal UI behavior after it has been saved.

### Application boundary

SecureAuth runs as an Android application in its own application sandbox. Application code can access the locally stored encrypted secret and account label through the app's storage APIs.

### Device boundary

The Android operating system, application sandbox, and Android Keystore are treated as trusted platform components. The current design relies on the device's security controls to protect the Keystore key and app-private storage.

### Keystore boundary

The AES key is generated in the Android Keystore under the `secureauth_totp_key` alias. The application requests a 256-bit AES key for GCM encryption and decryption, with randomized encryption required. The raw key material is not stored in SharedPreferences. The cipher provider generates the encryption IV, which is stored alongside the ciphertext.

If the Keystore key is invalidated, unavailable, or no longer usable, decryption fails and the application reports that it could not unlock the saved account. The application does not silently generate a replacement key for existing ciphertext.

### Storage boundary

The encrypted TOTP secret, initialization vector, and account label are stored in app-private SharedPreferences named `secureauth_accounts`. The secret is encrypted before persistence, while the account label is stored as ordinary application data. The storage format and preference keys remain unchanged.

### External service boundary

There is no backend or network service in the current implementation. TOTP generation is performed locally from the stored secret and the device clock.

## 3. Authentication and authorization model

SecureAuth is an authenticator rather than a conventional user-account authentication service.

- There is no server-side user registration flow.
- The unused `Login` and `Register` activities and their layouts have been removed.
- There is no password credential store.
- There is no bearer access token, refresh token, cookie session, or server-side session state.
- There are no application roles or permission checks.
- Access to the stored TOTP secret is governed by the Android application sandbox and the device security model rather than by an application-level authorization service.

The TOTP code generated by SecureAuth is an authentication factor intended for use with an external service. SecureAuth does not validate that code against an external identity system.

## 4. Current data flow

1. The user enters an optional account label and a Base32 TOTP secret.
2. The secret and label are validated locally.
3. SecureAuth obtains or creates a 256-bit AES key in Android Keystore.
4. The secret is encrypted with AES-GCM using a fresh provider-generated initialization vector.
5. The encrypted secret, IV, and account label are synchronously persisted in app-private SharedPreferences.
6. On restart, the encrypted secret is decrypted locally through the Keystore-backed key.
7. TOTP codes are generated locally and displayed without repopulating the secret field.
8. Account deletion synchronously clears the local SharedPreferences data and deletes the app-owned Keystore key.
9. The code refresh loop runs only while the activity is started and is removed when the activity stops.

## 5. Threats considered

| Threat | Current control | Residual limitation |
| --- | --- | --- |
| TOTP secret exposed in plaintext storage | AES-GCM encryption with a 256-bit Android Keystore-backed key | Compromise of the running app/device can still expose plaintext to the app process |
| Secret accidentally displayed after restore | Secret input is cleared after restore | Future UI changes must preserve this property |
| Reuse of a static encryption IV | Cipher provider generates a fresh randomized GCM IV for each encryption | Existing data has no additional authenticated metadata beyond the GCM authentication tag |
| Unauthorized access by another normal app | Android application sandbox and app-private storage | A compromised/rooted device is outside the normal trust model |
| Network interception | No network permission or network path for TOTP secrets or generated codes | No remote synchronization or recovery exists |
| Backup or restore of encrypted data without its Keystore key | Android application backup is disabled | No backup or recovery path is provided |
| Screenshots or recents thumbnail expose codes | `FLAG_SECURE` is set in non-debuggable builds | Debuggable builds intentionally allow screenshots; privileged device compromise is outside scope |
| Background refresh work | Handler callbacks are removed in `onStop` and cleaned up in `onDestroy` | Code refresh depends on the activity lifecycle and device clock |
| Unsafe account label content | ISO control characters rejected; trimmed label length limited to 64 | Label is not encrypted and is not treated as a secret |
| Ciphertext tampering | AES-GCM authentication is checked during decryption | Android Keystore/device implementation remains trusted |

## 6. Assumptions

- The Android platform and Keystore implementation are trusted.
- The device is running a supported Android environment with functioning application sandboxing.
- The user protects the physical device and its unlock credentials.
- The device is not intentionally rooted or compromised at the operating-system level.
- The user does not enter real TOTP secrets into an untrusted build of the application.
- The device clock is sufficiently accurate for RFC 6238 TOTP generation.

## 7. Current limitations

- There is no user authentication layer protecting the app itself.
- There is no biometric or device-credential gate implemented by SecureAuth before revealing generated codes.
- There is no multi-account model; the current storage implementation represents one active account.
- There is no encrypted backup, export, or recovery mechanism. Android backup is disabled.
- There is no remote synchronization or backend.
- The TOTP secret exists in process memory while the app is active.
- Debuggable builds allow screenshots; non-debuggable builds prevent screenshots and recents capture through `FLAG_SECURE`.
- The application ID is `io.github.aaqibhafeezkhan.secureauth`; upgrading from the earlier application ID installs separately and does not migrate existing saved accounts.
- Security behavior has not been comprehensively validated on a physical device or emulator in this environment.

## 8. Scope and roadmap

Epic #8 is tracked in [GitHub issue #8](https://github.com/Aaqibhafeezkhan/SecureAuth/issues/8). Its phases map to the current local-only application as follows:

- Phase 0, threat model and authentication baseline: documented for the local authenticator model.
- Phase 1, credential validation: implemented for Base32 TOTP secrets and account labels.
- Phase 2, local credential lifecycle: synchronous preference clearing and Keystore key deletion are implemented.
- Phase 3, authorization: backend roles and protected routes are not applicable without authenticated identities or a backend. The Android application sandbox remains the current boundary.
- Phase 4, abuse resistance: login brute-force controls and server lockout behavior are not applicable because there is no login service. Device-level access controls remain outside the app's current scope.
- Phase 5, API and input security: request validation, CORS, and CSRF controls are not applicable because no backend or API exists. Local TOTP and label validation are covered.
- Phase 6, testing: RFC TOTP vectors, validation boundaries, encrypted storage round trips, randomized encryption, tamper detection, and deletion have regression tests. Device-dependent tests require execution on an emulator or device.
- Phase 7, configuration and secrets: no application credentials or signing material are committed; release signing remains a local owner-managed task.
- Phase 8, documentation: this threat model, README, security policy, contribution guidance, and changelog describe the implemented scope and limitations.
- Phase 9, release validation: local build and device validation remain necessary before publishing a release.
- Phase 10, end-to-end readiness: not claimed. The project should not be described as production-ready until the applicable build, device, and security validation has been completed.

Future work should remain aligned with the local-only model unless a real backend is introduced. Relevant candidates include a biometric or device-credential gate, multiple accounts, QR import, broader TOTP algorithm support, and encrypted export with storage versioning and authenticated metadata.
